# Deployment runner: validation log

The record of `tools/deploy.py`, written while it was built on 25 November 2026. As in the other logs: **seen** means output or a screen was sent to me, **reported** means the user said so, **not run** means nobody has run it. Of the runner, `preflight` was seen on a tenant three times on 25 November, and `plan` twice: once up to the capacity question, once to its end. `apply` and `status` on a tenant are **not run**.

## What was asked

That changes two rules of the first list, by the person who wrote it: "never create or reassign capacity", and a workspace of the runner's own. The fourth issue follows the new instruction and keeps what is left of the old ones: see the decisions marked fourth issue.

On 25 November at 16:35, a few minutes after the fourth issue went out, the user wrote: "one more thing, I don't want a pre-populated .env file. On 25 November at 18:08, with the first plan on a tenant just read and no apply run yet, the user sent a second written specification, without a word beside it: "Harden the existing Northwind Ridge deployment runner and make repeat deployments require fewer interactions. ## Decisions

| Decision | Why |
|---|---|
| The runner signs in as the operator, through the Azure CLI | Several operations accept a person only (the Custom Locations lookup, the agents, notebooks that use semantic link). The edge keeps its managed identities, as in the guides |
| The suffix goes on names that must be unique outside the workspace; items inside keep their names | The notebooks and the app find `WindFarmEH` and `WindFarmLH` by name, and nothing can take a name inside a workspace the runner made |
| An approval covers the target, the options, every step and the files it uses, and any drift; not which steps are done | So one approval resumes an interrupted apply, and anything that changes what would happen voids it |
| A gate that has passed keeps its result | A stopped VM at night is not a reason to refuse Phase 2. `status` shows the freshness of now |
| Unknown things in the group or the workspace stop the runner; `--acknowledge` names one that belongs | "Stop on unrelated resources" without a way forward would end a deployment on the first policy-made resource |
| Notebook 04 is imported and not run | It changes nothing, and a job's output is read by nobody |
| The capacity is the operator's to name. The runner takes one by itself only when it is the single usable one in sight (third issue) | The rules say to stop on ambiguous matches and never to create or reassign a capacity. "The only one listed" turned out not to mean "the one to use" (R19) |
| Three answers that hold for a day are asked once in twelve hours, "could not be read" included (third issue) | A run looks at every step, an apply twice. On a line where a question stands for a minute, asking it each time is most of the run (R25). A block is never kept, so nothing that has to be fixed is hidden |
| The runner asks, in preflight and plan, in a terminal; an answer is a line of the settings and of the plan, never a change in Azure or Fabric (fourth issue) | The user asked for questions in place of edits to the settings file. The rules "read-only by default" and "apply only with the approval of a plan and its target" stand: a question changes what the plan says, and the plan is still read and approved. Without a terminal nothing is asked, so a pipeline behaves as before |
| A capacity is made only on a yes to that question and with its own approval; it is never paused, resumed, resized or deleted by the runner (fourth issue) | The first list said "never create or reassign capacity". Its author now asks for creation as a choice. A capacity costs money while it runs, so making one gets the treatment the list gave role changes: its own approval, which the yes gives for the plan of the same run and `--approve-capacity-creation` gives otherwise. Everything else of the old rule stays |
| The new capacity lives in the demo's resource group, with the deployment's tag and the suffix in its name (fourth issue) | Ownership by resource ID and a mark, as for everything else the runner makes; and the clean-up that removes the group removes the capacity, so that nothing that costs money is left behind without a record |
| F16, as asked; another SKU by a setting, not by a question (fourth issue) | The user named the SKU. A question about it would be one more thing to answer for the one person who has run this |
| The region for a new capacity: the edge's own, unless Microsoft's region table lists something the demo uses as missing there; then the next one that lacks nothing. A dated copy of the table is in the code (fourth issue) | "A proper region" had to mean something that can be checked. The table changes; a copy with its date can be wrong, so it proposes and cautions, and blocks only when a phase that was asked for needs what the table lists as missing (R30) |
| An existing workspace is taken only when it is empty and on the chosen capacity, and is held by its ID (fourth issue) | The first list asked for a dedicated workspace, known by ID and recorded ownership, and for a stop on unrelated resources. An empty workspace that the person picked is dedicated from then on. One with items is not, whatever the items are called |
| The resource group is not asked about (fourth issue) | The runner's proof that a group is its own is the tag it sets when it creates the group. Taking an existing group means writing to a resource somebody else made. Not built until it is asked for |
| The settings of a deployment are kept beside its checkpoint, `.deploy/<suffix>/demo.env`. The runner reads and writes nothing in `config/` (fifth issue) | The user wants no settings file prepared, and builds the demo again and again. Settings and checkpoint are two halves of one record: which names, and what was made under them. Kept together and by suffix, a second deployment cannot overwrite the first, and `config/demo.env` goes back to meaning one thing, a deployment by hand |
| They stay a file in the shell's format (fifth issue) | Every script reads its settings by sourcing a file, and the runner starts those scripts. Settings kept only inside the checkpoint would have to be written out as such a file for each script anyway, and a person could no longer read them or hand them to a script |
| One folder holds many deployments. `.deploy/current` names the one that commands work on; `plan --new` starts one, `--deployment SUFFIX` goes back to one (fifth issue) | "Over and over in the same tenant or new tenants". A new copy of the folder for every build was the only way before, and `--new-names` was refused as soon as anything existed |
| A new deployment in the same subscription takes over four things: the region of the edge, the VM sizes and their order, the shutdown hour, the Custom Locations object ID. Never a name, the capacity or the workspace (fifth issue) | The four are what a person settles once for a subscription, and the last is a lookup that needs a directory right. A capacity may be gone or paused by the next build and a workspace is the deployment's own, so those two are asked again. In another subscription nothing is taken over: none of it need hold there |
| The runner offers a new deployment by itself only in a terminal, and only in two cases: signed in to another subscription, or the deployment's resource group is gone (fifth issue) | Both mean that going on with the current names leads nowhere, and both are what "the next build" looks like in practice: a new tenant, or a clean-up. Without a keyboard it starts nothing by itself, so a pipeline never changes its target because of what it found |
| A script started by hand takes the file `ENV_FILE` names, then `config/demo.env`, then the current deployment's settings (fifth issue) | A deployment by hand in the same folder keeps working exactly as its guides say, and beside a deployment of the runner the same commands work without an option. The clean-up shows what it would remove before it removes anything, by name |
| A region that Azure's list of SKUs does not name for a new capacity is said, with the list, and left to the person at the question; the plan then shows `NOT CHECKED` and the request for the capacity decides. Written into the settings by hand, without that yes, it blocks (sixth issue) | The runner read that list wrongly once and left a person at a question with no way on (R47, R49). The request is the second thing an apply makes, so letting Azure decide costs nothing, and making a capacity keeps its own approval. A pipeline, which cannot be asked, keeps the stricter rule |
| A choice is settled by an option, then the deployment's settings, then the profile of the tenant and subscription, then a default the cloud establishes as the only one. What is left is asked together or blocks the plan (seventh issue) | The order of the specification of 18:08. The questions of the fourth issue stay, as the last resort and, with `--ask`, as a full round: one person asked for them the same afternoon |
| A new deployment is written without a region. The only default taken from discovery is a single capacity that can hold the demo (seventh issue) | "Never silently change geography." Up to the sixth issue a deployment started with nobody at the terminal took the region of the template, which nobody had chosen (R60). A single usable capacity adds no cost and is where it is; two are a choice |
| The profile is saved on request, per tenant and subscription, and never holds a name, a workspace or the choice to make a capacity. The fifth issue's taking-over from the previous deployment is gone (seventh issue) | "A reusable profile scoped to the tenant and subscription"; "do not inherit permission to create a paid capacity from another deployment". Taking over by itself was inheritance nobody had approved (R59) |
| An apply names its deployment, and every call of the Azure CLI names the deployment's subscription. The directory is read through Microsoft Graph with a token for that subscription (seventh issue) | `.deploy/current` and the CLI's active subscription are both changed by other terminals. `az ad` cannot be given a subscription (R51), so it is not used |
| Under the runner the scripts get the subscription by name and add it to each `az` call; by hand they are unchanged (seventh issue) | The scripts ran on a tenant as they are, by hand, and their 152 scenarios describe that. A wrapper that is only there when the runner sets a variable changes nothing for either |
| The approval is the digest of a saved plan: who, where, every setting, the approvals, and every file that changes what a step does, with what scripts read or ship. A refusal says what differs (seventh issue) | "Make plan approval cover what actually runs." The earlier identifier covered a step's own files and seven facts of the target (R55), and a refusal could only say that something had changed |
| A notebook run is taken only when its ID is in the checkpoint. An intent without an ID, and a run in progress nobody recorded, are handed to the person with `--adopt-job` and `--resubmit` (seventh issue) | Run On Demand Item Job documents nothing by which a run could be matched to a request, and the notebooks write data. The earlier runner waited for any run in progress as if it were its own (R54) |
| Each deployment builds the app in a folder of its own (seventh issue) | The app's copy of `config.ts` names one workspace, and the app's tool keeps state in the folder. A lock on one shared folder would have kept two builds apart in time and not their state (R57) |
| `provisioned`, `blocked` and `demo-ready` are reported apart. For the twin, demo-ready needs the deployed app's own check, given by a person (seventh issue) | The runner's check after Phase 4 is a query with the operator's token; the app reads as another identity. There is no documented way to ask the deployed app |
| A Fabric Environment for the `%pip` notebooks was looked into and not built (seventh issue) | The API parts are documented. Building it changes five notebooks that ran on the tenant in their present form, and three things about it are unproven; one run by hand in the pilot settles them. The guide has the finding |
| The clean-up removes nothing on a guess: with several deployments in a folder it wants `--deployment`. Its confirmations stay as they were (seventh issue) | "Use the selected deployment's explicit scope and retain a separate teardown approval" |
| What the runner could not read is shown as `NOT CHECKED`, never as `done` (third issue) | A step is not complete because a command returned, and a check is not made because it did not stop anything (R21) |
| The twin's live route is a step of the runner: `p4.eventhouse_principal` makes the service principal by starting `app/create-principal.sh`, and `p4.deploy_secrets` deploys the app again. Both are left out with `--lakehouse-only` (fifteenth issue) | Asked for on 26 November, 17:13. The script ran on this tenant on 23 November; the runner builds on it and writes no second implementation. A tenant that lets nobody register an application must still be able to finish Phase 4 |
| It waits for `--approve-role-changes`, and its line of the plan says what is made in the directory (fifteenth issue) | It gives a role in the workspace, which is a scoped role change. An app registration is no tenant setting, no capacity and no broad access; the plan that is approved names it, its secret and its role |
| Each deployment has an app registration of its own, named with its suffix (fifteenth issue) | `az ad app credential reset` replaces every secret of a registration. One name for all deployments would let each new one take the twin of the one before it off its live route (R81) |
| Notebooks 06, 07 and 08 are run by the runner without an option; `--no-pip-jobs` leaves them to the person. Notebook 09 as well once `--allow-preview data-agent-sdk` is given (seventeenth issue) | They ran as jobs on the tenant at the first try (R86), and he asked why the runner had not run them. "Put preview integrations behind explicit opt-in": the pre-release SDK of notebook 09 keeps its own. A job that fails still hands the notebook back |
| With `--allow-preview operations-agent` the runner creates the operations agent with its instructions and its data source, stopped, and reads its definition afterwards. It never writes a playbook and never starts an agent (seventeenth issue) | His choice of 20:39. "Prefer GA features. Put preview integrations behind explicit opt-in and leave undocumented operations manual." Create Operations Agent and its definition are documented, in preview; of the playbook the article says to send an empty object. "Do not guess payloads": one request in the documented form, and a refusal goes back to the person with Fabric's line |
| The step of the agent is two steps then: the item, which the runner makes, and the playbook, the start and Teams, which are his and which the runner checks in the definition (seventeenth issue) | "Do not mark a step complete merely because a command returned successfully": an item that exists is not an agent that watches. With the definition readable, the runner can at least see a playbook and `shouldRun` |
| The runner never holds the secret. What it keeps is the time the registration's newest secret was made, as the directory gives it (fifteenth issue) | "Never log tokens, connection strings, secret values". The time is enough to see that the app holds the present secret, and that somebody has replaced it since |
| For a deployment with the service principal, demo-ready needs the twin's check to pass on the Eventhouse route (fifteenth issue) | The Lakehouse route always passes when the data is there; with the principal set up, a check that passes on it alone means the live route does not work, which is what the demo is to show |
